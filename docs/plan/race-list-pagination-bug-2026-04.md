# レース一覧ページの総ページ数判定バグ（2026-04-26〜）調査メモ

## 発端

[plan/regional-racing-model.md](./regional-racing-model.md) の地方競馬パイロット実行前の
下調べ（`get_race_list` がNARを含むか、月あたりの件数はどれくらいか）で、
`RaceListParser.parse_total_pages()` が壊れていることを発見した。

## 根本原因（確定）

`class="pager"` のdivは実際には「1,717件中1~100件目」という**件数サマリーのテキストのみ**を
持ち、ページ送りリンク自体はこのdivの外（`<li>`要素、pagerクラスなし）にある。旧実装は
`pager` div内の `<a href="page=...">` を探していたため常に0件ヒットし、**総ページ数は常に1と
誤判定**されていた。

修正: 件数サマリーのテキスト（`X件中A~B件目`）から総件数・1ページあたり件数を直接算出する
方式に変更（[scraper/scraper/parsers/race_list.py](../../scraper/scraper/parsers/race_list.py)）。
コミット `848540b`。

## 影響範囲（2026-08-11判明、[odds-scraping-bug-2026-04.md](./odds-scraping-bug-2026-04.md) より深刻）

このバグは `scrape_backfill`/`scrape_incremental`（本番差分取得の中核）が使う
`get_race_list` の全ページ走査に直結する。1ヶ月の対象件数が100件を超えると2ページ目以降が
黙って欠落する。

このリポジトリのscraperが実運用で稼働を開始した **2026-04-26** 以降、月あたりの対象件数は
（中央競馬4場のみだった頃と異なり）地方競馬14場を含めて **月1,700件規模** に達していたため、
**ほぼ毎月このバグを踏み続けていた**。

実測（本番DB、2026-08-11時点）:

| 月 | DB内件数（全venue合算） | 実際の総数（netkeiba側実測） |
|---|---|---|
| 2026/04 | 219件 | 不明（中央競馬4場+地方混在の移行期） |
| 2026/05 | 260件 | 概算1,700件規模 |
| 2026/06 | 207件 | **1,717件（実測）** |
| 2026/07 | 248件 | 概算1,700件規模 |

→ **実際の総数の1〜2割程度しか取得できていなかった**。中央競馬4場（中山・東京・京都・中京）
だけで見ても、6月は東京16件・7月は中京1件のみで、明らかに欠落している。地方競馬だけでなく
**中央競馬の直近データも大きく欠けている**点が [odds-scraping-bug-2026-04.md](./odds-scraping-bug-2026-04.md)
（確定オッズのnullのみだった）との違い。

念のため、ローカルDB（別途独自にスクレイピングしていたもの）とも比較したが、同じコードの
同じバグを踏んでいたため、ほぼ同水準の欠落だった（ローカルの方が優れている、ということはなかった）。

## 対応

`scrape_incremental` を修正後のコードで 2026年4月〜現在の範囲で再実行し、既存データを
壊さず（`get_existing_race_ids` で重複除外）不足分だけを埋める。2026-08-11夜、本番ホスト上で
`nohup .venv/bin/python -m scraper.main incremental 2026 4` をバックグラウンド起動。
全venue対象・件数規模が大きいため完了まで日単位を要する見込み。

- [ ] キャッチアップ完了後、月別件数がnetkeiba実測値と近い水準になっているか再確認する
- [ ] 完了後、`check_missing.py` を一通り実行して他の欠損が無いか確認する
- [ ] 中央競馬モデルの現行テストセット（直近含む）の評価指標が、データ欠落の影響を
      受けていないか再計算する（[odds-scraping-bug-2026-04.md](./odds-scraping-bug-2026-04.md) の
      bootstrap CI定量化タスクと合わせて実施）
