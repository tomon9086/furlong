## ゴール

- **単勝（および複数券種）の回収率を 110% 程度に引き上げる**こと。
- フェーズ4時点の回収率 ≈ 80%（[improvement_plan.md](../improvement_plan.md)）。ただしこの 80% は EV（期待値）を使わずに「`win_prob` 最大の馬を機械的に1点買い」した数字で、回収率最適化を行った結果ではない。
- 発端は対象レース `202605021011` の予測（4番を `win_prob 0.19` で1位予測 → 実際11着）だが、**単一レースの当落はノイズ**。判断はテスト期間全体の回収率で行う。

## 大前提：回収率 ≠ 予測精度

- 的中率を上げる最短手段は人気馬を買うことだが、人気馬は低オッズなので回収率は伸びない。
- 逆に的中率が低くても、**オッズに対して過小評価された馬・券種（`EV = 確率 × オッズ > 1`）だけを選んで買えば**回収率はプラスになりうる。
- つまり 110% は「当てる」問題ではなく「**割安な対象を選んで買う**」ベット選択の問題。精度改善は手段であって目的ではない。

## 回収率を動かす3レバー

| レバー | 内容 | 現状 |
|---|---|---|
| **1. オッズの取得** | EV を計算する材料そのもの | **実装済み**。`pre_race_odds` から `win_odds` を取得し EV 計算まで動作 |
| **2. 確率の較正（calibration）** | `EV = p × odds` の `p` が正確であること | IsotonicRegression による後段較正を実装済み。calibration curve で評価可能 |
| **3. 賭け対象の選択** | EV 閾値・券種・人気帯で買い目を絞る | EV フィルタ（閾値1.5）＋MC シミュレーション推奨ロジック実装済み |

全レース・全頭を買えば控除率（≒20%）の分だけ必ず負ける。**買わない判断**が回収率の中核。

## +30pp（80%→110%）の出どころ

控除率20%の壁を越えるには「市場の歪み」を取りに行く必要がある。市場オッズを生特徴量として学習すると市場の模倣になり上限が控除率分（≒80%）で頭打ちになる（[prediction-accuracy.md](./prediction-accuracy.md)）。狙える歪みの候補：

- **人気-穴馬バイアス（favorite-longshot bias）**：穴馬は過剰に買われ回収率が低く、人気サイドに妙味が残りやすい。競馬で最もよく知られた歪み。`evaluate_by_popularity` で傾向を確認できるはず。
- **券種選択**：単勝・複勝は市場が効率的で勝ちにくい。三連単など難解な券種は偏った買いで歪みが大きい＝妙味はあるが分散も大きい。
- **点数を絞る**：カバレッジを犠牲にして高EVのみ。回収率とのトレードオフ。
- **市場に先行する特徴量**：市場が織り込む前の情報で `p` を作れれば、その差分がそのままエッジになる。

## オッズの扱いの整理（重要）

「特徴量に入れるか」と「買い目選定に使うか」を分ける。

- **生特徴量としては入れない**（市場模倣 → 80%上限）。方針どおり。
- **買い目選定（EV 計算）には事前オッズが必須**。現状オッズ未取得で EV フィルタが死んでおり、これは方針と無関係な実装上の穴。
  - 改善：締切前（前日／当日朝）の暫定オッズをスクレイプ → **学習には渡さず、EV 計算と買い目選定のみに使う**。
- 発展：モデル予測と市場の乖離（`model_prob / market_prob`）を「市場が過小評価している馬」検出のシグナルにする（= 人気-穴馬バイアスの定量化）。

## 評価をROI中心に組み替える

- **回収率を主指標に**。学習の objective（logloss）より、「EVフィルタ後の回収率」を最大化する**閾値・券種・人気帯の設計**が効く。
- **確率較正の評価**（Brier score / calibration curve）を `evaluation.py` に追加。「19% と出した馬群が実際に約19%勝つか」。EV 判定の信頼性の土台。[improvement_plan.md](../improvement_plan.md) C 群には未記載。
- **サンプル設計が決定的**：回収率は分散が大きい。**110% が誤差でないと言うには数千ベット規模が必要**。100ベットの110%は無意味。bootstrap で信頼区間を出す（[improvement_plan.md](../improvement_plan.md) C-2）。
- **walk-forward（rolling）検証**：単一分割の `split_by_date` より、複数期間で回収率の安定性を見る。

## 推奨着手順（回収率ドリブン）

1. **事前オッズ取得 → 真の回収率を測定**
   EV を使えていない現状の数字は起点として不正確。まずオッズを取り、EV フィルタを稼働させる。回収率改善のすべての前提。
2. **確率較正の可視化（Brier / calibration curve）**
   `p` が信用できるかを先に数値化。EV 判定の信頼性を担保する土台。
3. **EVフィルタ × 券種 × 人気帯のグリッドで回収率を最適化**
   全レース買わず、どこに妙味（人気-穴馬バイアス等）が残るかを実測。bootstrap で 110% が有意かを判定。
4. **lambdarank 化／特徴量追加で `p` の質を底上げ**（[improvement_plan.md](../improvement_plan.md) B-4・A 群＋上表）
   より良い `p` を通じて**間接的に**回収率へ効く。主役はあくまでベット選択。

## 次のアクション（優先順）

### 1. 較正を out-of-sample に修正（最優先）

**問題**: 現在の Isotonic Regression は「テストデータでフィット → 同じテストデータで評価」の in-sample 較正。EV 判定の信頼性が過大評価されている可能性がある。

**対応**: train / val / test の 3 分割に変更し、val で較正し test で評価する構成にする。

- `split_by_date` で train/val/test を 6:2:2 程度に分割
- `val` で `calibration.calibrate_models` を実行
- `test` で EV グリッド・bootstrap CI を評価

### 2. EV×7番人気以下×馬連戦略の Bootstrap CI 算出

**問題**: 「EV≥2.0 × 7番人気以下 × 馬連で 137%」がノイズか真のエッジかを判定できていない。

**対応**: `evaluation.py` に bootstrap 信頼区間算出を追加し、95% CI の下限が 100% を超えるかを確認する。

- 1,098 件のサンプルに対して bootstrap（例: 10,000 回リサンプル）で 95% CI を算出
- フォールド別（walk-forward）でも同戦略の回収率を確認し、安定性を検証

### 3. Walk-forward での EV×馬連戦略の安定性確認

**問題**: `ev_multi_bet_grid` はホールドアウト分割のみで評価しており、walk-forward での挙動が不明。

**対応**: walk-forward の各フォールドで「EV≥1.5 × 7番人気以下 × 馬連」回収率を測定し、全フォールドで一貫して高いかを確認する。

### 4. Optuna ハイパーパラメータ最適化

**問題**: モデルパラメータがほぼデフォルト値（`num_leaves=63, lr=0.05, num_boost_round=500`）。近年フォールドの回収率低下は過学習の可能性があり、パラメータ調整で改善できるかもしれない。

**対応**: Optuna で `num_leaves`, `learning_rate`, `min_child_samples`, `feature_fraction` を探索。評価指標は walk-forward 平均回収率を主軸にする。

## 特徴量要件定義：調教師・騎手の「通算」勝率（2026-08-01）

`analysis/notebooks/03_recovery_rate_by_condition.ipynb` 軸10・12で見つかった歪み（調教師24.3pt差、騎手16.6pt差、いずれも循環性チェック済み）を特徴量として取り込むための要件。**まだ実装前・未検証**、ここでの決定事項もすべて仮。

### 既存特徴量との違い（重複ではない）

`predictor/predictor/preprocessing.py` には既に騎手・調教師の統計量があるが、ノートブックで効いた軸とは条件が異なる。

| 特徴量 | 集計窓 | 条件 |
|---|---|---|
| `trainer_win_rate_last30`（既存） | 直近30走のみ | 条件なし |
| `jockey_win_rate_venue_cond`（既存） | 全期間累積 | `venue` × `course_type` で絞り込み |
| **今回追加したいもの** | **全期間累積（デビューからそのレース直前まで）** | **条件なし・累積騎乗数の下限あり（ノートブックでは調教師500件・騎手500件）** |

直近30走は「今の調子」、venue×course_type限定は「その条件への適性」を捉える一方、ノートブックが検出したのは**キャリア全体の実力差**（「仕上げが上手い調教師/腕の良い騎手」という安定した属性）で、既存特徴量ではカバーされていない軸。

### 追加する特徴量

- `trainer_prior_win_rate`, `trainer_prior_mounts`
- `jockey_prior_win_rate`, `jockey_prior_mounts`（`jockey_win_rate_venue_cond` とは別軸として併存させる）

**tier化（下位/中位/上位）はせず、連続値（勝率 + 騎乗数）をそのまま渡す**方針。理由：
- LightGBM は木構造なので非線形の閾値を自動で学習でき、tier化による情報の削ぎ落としが不要。
- ノートブックの tier 閾値（`TRAINER_LOW_MAX=0.05` 等）は「全期間データ」から一度だけ求めた値で、可視化用としては妥当だが、学習/検証期間をまたいで求めた定数を特徴量に焼き込むと将来データの情報が閾値経由で紛れ込む余地がある。連続値で渡せばこの問題を回避できる。
- `prior_mounts` も一緒に渡すことで、モデル側に「累積騎乗数が少ない＝勝率の信頼度が低い」ことを学習させる（欠損埋めではなく生の値で渡し、閾値未満を欠損にするかは要検証）。

### 計算方法（学習時）

`compute_recent_stats()`（`preprocessing.py`）に、既存の `jockey_win_rate_venue_cond` / `trainer_win_rate_last30` 計算ブロックと同じ場所へ追加。ロジックはノートブックの `compute_prior_stats` をそのまま移植：

1. `(entity_id, date)` 単位で日次の騎乗数・勝利数を集計（同日複数レースの前後関係は分からないため、日付単位でまとめてから1日分ずらす）。
2. `entity_id` ごとに日次集計を累積し、`shift` して「そのレースより前」の値にする。
3. 累積騎乗数が閾値未満の行は欠損（NaN）のままにする（LightGBM は欠損を扱えるため補完しない）。

この方式は `shift`/`cumsum` ベースで、既存の `jockey_win_rate_venue_cond` と同じ「当該レース自身を含めない」設計を踏襲するため、時系列リークは既存パターンと同様に発生しない。

### 計算方法（予測時）

`load_predict_data` 用に、`_TRAINER_WIN_RATE_QUERY` と同様の全期間累積版 SQL クエリが別途必要（既存の直近30走クエリとは別物）。対象日付より前の全レースを集計する形になる。

### 未決定・要検証事項

- 累積騎乗数の下限値（ノートブックは調教師・騎手とも500件を仮置き）は訓練データのみから決めるべきか、固定値のままでよいか。
- 騎手・調教師は起用関係で相関しうる（ノートブックの「次にやること」参照）。両方を特徴量に入れた場合にモデルが多重共線性でどちらかを潰してしまわないか、追加後に重要度を確認する。
- 効果は人気帯によって偏り、7番人気以下でしか出ていない（ノートブック軸10・12）。人気帯との交互作用をモデルが自動で学習できるかは実際に追加して確認するしかない。
- ノートブックの回収率はいずれも100%未満（最大でも調教師上位74.9%）なので、**この特徴量単体で回収率が黒字化するわけではない**。既存のEVフィルタ・券種選択と組み合わせて初めて意味を持つ、という前提を見失わないこと。

### 検証計画

tune の教訓（Optuna の「最良パラメータ」が通常splitで悪化した）を踏まえ、特徴量追加も同じ2段階で検証する。

1. `compute_recent_stats` に追加後、`get_feature_columns()` に組み込み、`python -m predictor.main train` を実行（train/val/testの標準split + bootstrap CI + walk-forward）。
2. 追加前後で `win_logloss` / `recovery_rate`（特に7番人気以下）を比較し、walk-forwardの全フォールドで一貫して改善するかを確認してから正式採用・`spec.md` へ記録する。
